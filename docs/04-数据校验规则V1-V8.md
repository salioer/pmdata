# 04 数据校验规则 V1–V8

## 一、总体说明

| 编号 | 校验对象 | 主要解决 |
|---|---|---|
| V1 | 工时填报完整性 | 填了没有 |
| V2 | 里程碑质量 | 里程碑时间可不可信 |
| V3 | 工时挂对需求 | 工时填对了需求没有 |
| V4 | 需求数与规模档 | 需求数和定档准不准 |
| V5 | 资源池对账 | 名册和报工人员对不对得上 |
| V6 | 需求状态与归属 | 状态和战场归属对不对 |
| V7 | AI 遥测覆盖 | AI 工具数据覆盖了多少 |
| V8 | 跨系统一致性 | antom、发布系统与 iSmart 是否一致（新增） |

V1–V7 沿用内部已有定义，本文补充具体规则；V8 为新增。

**统一要求**
- **阈值**：下文阈值均为初始值，P0 跑出底数后按实际分布校准一次。
- **输出**：每条规则每周产出一份异常清单，按战场推送给战场接口人，写明责任人和关闭标准。
- **粒度**：异常清单可以到需求级；涉及个人级数据的规则，只给治理负责人看明细，看板只出战场 / 团队级汇总。
- **红绿灯**：每条规则按阈值判定绿 / 黄 / 红，汇总为 Q01 达标率。

## 二、规则明细

### V1 工时填报完整性

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V1.1 缺填率 | 应填未填人周 ÷ 应填人周（应填 = V5 对账后的在册人员 × 工作周） | ≤ 3% | 3–8% | > 8% |
| V1.2 迟填率 | 超过截止时间才填报的人周 ÷ 已填人周 | ≤ 10% | 10–25% | > 25% |
| V1.3 模板化满填率 | 整周 5 天都挂同一需求且每天恰好 1 天的人周 ÷ 已填人周 | ≤ 20% | 20–40% | > 40% |
| V1.4 超填 | 单周超过 5 天或单日超过 1 天的记录数 | 0 | 1–5 | > 5 |

> V1.3 只是信号，不代表一定填错（专注做一个需求是正常的），用于发现敷衍填报的团队。

### V2 里程碑质量

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V2.1 时序违规率 | 不满足"立项 ≤ 评审 ≤ 开发开始 ≤ 提测 ≤ 上线"的需求占比 | ≤ 2% | 2–5% | > 5% |
| V2.2 未来日期 | 实际日期晚于今天的里程碑数 | 0 | 1–5 | > 5 |
| V2.3 照抄率 | 所有里程碑的计划日期与实际日期完全相等的需求占比 | ≤ 10% | 10–30% | > 30% |
| V2.4 集中补录率 | 录入时间晚于实际日期 7 天以上的里程碑占比 | ≤ 15% | 15–35% | > 35% |
| V2.5 上线日偏差 | iSmart 实际上线日与生产发布日期相差 3 天以上的需求占比 | ≤ 5% | 5–15% | > 15% |

### V3 工时挂对需求

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V3.1 状态不符报工 | 对未开始、已关闭、已取消的需求报工的人日占比 | ≤ 2% | 2–5% | > 5% |
| V3.2 非成员报工 | 报工人不在需求成员或所属团队中的人日占比（iSmart 有成员字段时启用） | ≤ 5% | 5–15% | > 15% |
| V3.3 公共工时占比 | 挂到"公共 / 杂项"类条目的人日占比 | ≤ 10% | 10–20% | > 20% |
| V3.4 已上线零工时 | 已上线但没有任何报工的需求占比 | ≤ 3% | 3–10% | > 10% |
| V3.5 交叉校验 | 抽样：报工需求所涉及的应用，与同一人提交 PR 的应用是否有交集（两侧人员标识先哈希脱敏，结果只出团队级） | 一致率 ≥ 70% | 50–70% | < 50% |

### V4 需求数与规模档

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V4.1 疑似重复 | 同战场、标题高度相似且创建时间相近的需求对数 | ≤ 1% | 1–3% | > 3% |
| V4.2 拆单异常 | 同一创建人 7 天内创建 5 个以上 XS 需求的次数 | 0 | 1–3 | > 3 |
| V4.3 人日异常 | 已上线但零人日的需求，或人日超过同档 P99 的需求占比 | ≤ 2% | 2–5% | > 5% |
| V4.4 档分布漂移 | 月度各档占比与前 3 个月均值相差超过 10 个百分点的档数 | 0 | 1 | ≥ 2 |
| V4.5 文档充分率 | 被大模型判为"文档充分"的上线需求占比 | ≥ 60% | 40–60% | < 40% |
| V4.6 系统识别召回率 | PR 样本上大模型识别涉及系统的召回率（见第 02 篇） | ≥ 70% | 50–70% | < 50% |
| V4.7 TL 档偏差率 | TL 档与大模型档不一致的需求占比（双轨期及之后） | ≤ 25% | 25–40% | > 40% |

### V5 资源池对账

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V5.1 在册未报工 | 名册在册但当月无任何报工的人数占比 | ≤ 2% | 2–5% | > 5% |
| V5.2 报工不在册 | iSmart 有报工但名册中不存在的人数 | 0 | 1–3 | > 3 |
| V5.3 离职后报工 | 离职或裁撤日期之后仍有报工的人数 | 0 | 1–2 | > 2 |
| V5.4 战场归属不一致 | 名册所属战场与 iSmart 报工人所属战场不一致的人数占比 | ≤ 2% | 2–5% | > 5% |

### V6 需求状态与归属

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V6.1 状态停滞 | 处于"开发中 / 测试中"但连续 3 周无报工的需求数 | ≤ 3% | 3–8% | > 8% |
| V6.2 已上线未关单 | 有生产发布记录 14 天后仍未关闭的需求占比 | ≤ 5% | 5–15% | > 15% |
| V6.3 归属为空 | 战场或模块字段为空的需求数 | 0 | 1–5 | > 5 |
| V6.4 归属不一致 | 需求战场与负责人所属战场不一致的需求占比 | ≤ 5% | 5–10% | > 10% |

### V7 AI 遥测覆盖

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V7.1 覆盖率 | 有 AI 工具遥测记录的人 ÷ 在册研发人员 | ≥ 80% | 50–80% | < 50% |
| V7.2 会话挂接率 | 能关联到需求 ID 的会话 ÷ 总会话 | ≥ 60% | 30–60% | < 30% |
| V7.3 Token 明细完整率 | 必填字段齐全的 Token 记录占比（P1 标准化后启用） | ≥ 95% | 80–95% | < 80% |

### V8 跨系统一致性（新增）

**链路一：antom ↔ iSmart**（解决漏同步和状态冲突）

| 规则 | 判定逻辑 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| V8.1 漏同步率 | antom 中存在、iSmart 中不存在的需求占比 | ≤ 1% | 1–5% | > 5% |
| V8.2 状态冲突率 | 按状态映射表比对，两边状态不一致的需求占比 | ≤ 2% | 2–5% | > 5% |
| V8.3 字段不一致率 | 战场、里程碑、排期月任一字段两边不一致的需求占比 | ≤ 3% | 3–10% | > 10% |
| V8.4 同步健康度 | 同步失败次数；同步延迟超过 24 小时的次数 | 0 | 1–3 | > 3 |

**链路二：发布系统 ↔ iSmart**（支撑定档核验和"上线"判定）

| 规则 | 判定逻辑 | 说明 |
|---|---|---|
| V8.5 PR 挂接率 | 已发布 PR 中 message 带有效需求号的比例 | 只用于判断核验样本是否够用，**不设硬门槛** |
| V8.6 需求覆盖率 | 已上线需求中至少挂上一个 PR 的比例 | 同上 |
| V8.7 状态反证 | iSmart"已上线"但无任何发布记录的需求数；有发布记录但 iSmart 未上线的需求数 | 绿 ≤ 2%，黄 2–5%，红 > 5% |
| V8.8 无效需求号 | PR 里写的需求号在 iSmart 不存在或已关闭的数量 | 绿 ≤ 2%，黄 2–5%，红 > 5% |

## 四、字段级权威源表

每个关键字段只认一个系统。两边冲突时，按此表裁决。

| 字段 | 权威源 | 说明 |
|---|---|---|
| 需求是否存在 | antom 战场：antom；其他战场：iSmart | iSmart 缺失的 antom 需求，计入 V8.1 漏同步 |
| 受理状态 | antom 战场：antom；其他战场：iSmart | — |
| 是否上线、上线日 | 生产发布记录 | 无发布记录挂接时，暂用 iSmart 实际上线日并打标记 |
| 排期月 | iSmart 月初冻结快照 | 冻结后不可修改 |
| 人日（报工） | iSmart | — |
| 在册人员、所属战场 | HR / PMO 名册 | — |
| 规模档 | 需求定档结果表 | 标明定档来源和尺子版本 |
| AI 费用 | Token 消耗明细 | P1 标准化后 |

## 五、antom ↔ iSmart 状态映射表

> 以下为示例，需按两个系统的实际状态值逐项填写确认。

| antom 状态 | 对应 iSmart 状态 | 备注 |
|---|---|---|
| 待受理 | 新建 / 评审中 | |
| 已受理 | 排期中 | |
| 开发中 | 开发中 | |
| 测试中 | 测试中 | |
| 已上线 | 已上线 | 以发布记录为准 |
| 已关闭 | 已关闭 | |
| 已取消 | 已取消 | |

**冲突裁决流程**（以"antom 未受理 / iSmart 已上线"为例）

```
查发布记录
 ├─ 有生产发布记录 → 判定为"已上线"，antom 状态滞后 → 通知 antom 战场接口人更新
 └─ 无生产发布记录 → 判定为"未上线"，iSmart 状态错误 → 通知 iSmart 需求负责人更正
```

裁决结果写入异常清单，关闭标准为两边状态与裁决结果一致。

## 六、个人级数据使用规范

涉及个人级数据的规则：V1、V3、V5、P02 的计算过程。

- **最小必要**：只取规则所需字段。
- **匿名聚合**：看板和对外报告只出战场 / 团队级汇总。
- **不进 KPI**：校验结果不用于个人绩效评价。
- **访问控制**：个人级明细只对数据治理负责人开放，访问需审批并留痕。
- **代码提交**：定档、核验和度量只取需求号、仓库、应用，不取提交人；唯一例外是 V3.5 交叉校验，需要把报工人和提交人对上，此时两侧人员标识先做哈希脱敏，结果只出团队级。
- **AI 会话**：只取统计特征，不取对话原文。
