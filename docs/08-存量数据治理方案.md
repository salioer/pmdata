# 08 存量数据治理方案

## 一、已知腐化点与对策

| 腐化表现 | 根因判断 | 对策 | 对应规则 | 优先级 |
|---|---|---|---|---|
| 需求漏同步：antom 有、iSmart 没有 | 同步链路没有对账和监控 | 存在性对账；同步失败告警；漏单清单闭环到战场接口人 | V8.1、V8.4 | **P0** |
| 状态冲突：antom 未受理、iSmart 已上线 | 没有字段级权威源，也没有状态映射 | 字段级权威源表；状态映射表；"上线"以发布记录为准 | V8.2、V8.7 | **P0** |
| 需求数不准 | 漏同步 + 拆单 / 重复 | 对账补齐；吞吐改用当量，拆单不再增加产出 | V4.1、V4.2、V8.1 | **P0** |
| 项目定档不准 | 依赖研发自填人日 | 大模型自动定档（知识库前提）；未就绪时 TL 兜底档并标"偏保守" | V4.4–V4.7 | P1 |
| 工时不准 | 敷衍填报、挂错需求 | V1 / V3 治理；北极星改用名册人日，降低对工时明细的依赖 | V1、V3 | P1 |
| 存量看板 / 报表口径混乱 | 同名不同义、僵尸指标 | 盘点后按四象限处置；新体系上线时同步下线被替代的旧指标 | — | P1 |

## 二、antom 同步治理

antom 战场使用自有项目管理系统，通过接口同步到 iSmart。漏单和状态冲突都出在这条链路上。

### 2.1 对账机制

| 步骤 | 做法 | 频率 |
|---|---|---|
| 全量比对 | 按需求 ID 比对两边的需求清单，找出单边存在的需求 | 每日 |
| 状态比对 | 按状态映射表比对两边状态，标出冲突 | 每日 |
| 字段比对 | 比对战场、里程碑、排期月 | 每周 |
| 同步监控 | 监控接口调用失败和延迟，超过 24 小时未同步即告警 | 实时 |

### 2.2 闭环

```
对账发现异常 → 生成异常清单（需求级）→ 推送 antom 战场接口人
 → 修复（补同步 / 更正状态）→ 次日对账确认关闭
```

**状态冲突**按第 04 篇的裁决流程处理：有生产发布记录的以"已上线"为准，没有的以"未上线"为准。

### 2.3 历史存量清理

P0 期间对 antom 近 12 个月的需求做一次全量对账，补齐漏同步的需求，更正冲突状态。基线期如果落在这 12 个月内，清理后才能用于校准。

## 三、存量看板与报表盘点

### 3.1 盘点表

每个现有看板、报表、指标登记一行：

| 字段 | 说明 |
|---|---|
| 名称 | 看板 / 报表 / 指标名称 |
| 所在位置 | 系统、链接 |
| 使用方 | 谁在看、多久看一次 |
| 口径说明 | 怎么算的 |
| 数据来源 | 取自哪个系统 |
| 最后更新时间 | 最近一次数据刷新 |
| 维护人 | 谁负责 |
| 可信度 | 高 / 中 / 低（对照 V 规则结果判断） |
| 与新体系的关系 | 对应新体系的哪个指标；无对应 |

### 3.2 四象限处置

```
                  可信度高
                     │
      合并到新口径     │     保留
   （口径对、但重复）   │  （纳入指标字典统一管理）
  ───────────────────┼───────────────────
        下线          │      重建
   （没人看、也不准）   │  （有人看、但不准）
                     │
                  可信度低
     使用频度低 ←─────┴─────→ 使用频度高
```

| 象限 | 处置 |
|---|---|
| 保留 | 纳入指标字典，统一口径和维护人 |
| 合并 | 与新体系中的对应指标合并，旧的下线 |
| 重建 | 按新体系口径重建，过渡期两套并行一个月后旧的下线 |
| 下线 | 通知使用方后直接下线 |

**原则**：新体系的指标上线时，被它替代的旧指标必须同步下线，避免两套数打架。

## 四、常态治理机制

| 机制 | 内容 |
|---|---|
| 单一口径源 | [指标字典](../metrics/指标字典.csv)是唯一的指标口径来源；任何看板引用指标都必须对应字典里的编号 |
| 数据 owner | 每个指标、每条 V 规则都有明确的维护人 |
| 源头校验 | 优先在 iSmart 侧做校验（必填项、状态流转规则、里程碑时序校验），事后清洗兜底 |
| 规则常态运行 | V1–V8 每周自动运行，异常清单每周推送 |
| 变更流程 | 口径变更需提交变更说明（改什么、为什么、影响哪些指标），经 PM 团队评审后更新指标字典和本文档，并在月报中公告 |
| 复盘 | 数据质量结果进入月度经营复盘，只进团队，不进个人 KPI |

---

## 五、治理原则

1. **源头优先**：能在录入时拦住的，不留到事后清洗。
2. **边度量边治理**：不等数据全部干净才出数，用数据门禁控制结论强弱。
3. **不依赖研发改变行为**：治理动作尽量落在系统对账和既有流程上，不新增研发侧的填报负担。
4. **只问团队，不问个人**：异常清单到需求级、责任人到战场接口人，不用于个人评价。
