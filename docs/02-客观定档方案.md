# 02 客观定档方案：大模型读需求自动定档

## 一、要解决的问题

规模档（XS / S / M / L）过去用人日划分，但人日是研发自己填的，不管预估还是实际都不准。更根本的问题是，**人日会随 AI 提效而下降**：一个原本 30 人日的 M 需求，用 AI 只花了 18 人日，就会掉进 S 档，提效被分档吃掉，看不出来。

我们需要一种**不随效能漂移、不新增人工填写**的定档方式。

**已经排除的方案**

| 方案 | 排除原因 |
|---|---|
| 研发 TL 改填规模要素 | 推行不了 |
| PR 强制带需求号，从发布记录自动采集 | 推了 4 个月仍难强制 |
| PM 填写规模要素 | PM 没有判断需求复杂度的能力 |

---

## 二、方案思路

让大模型来"读需求"：读需求文档，并结合本战场的产品知识库，提取几样**"要做什么"**的规模要素，再由程序按固定权重算分定档。

**为什么不漂移**：大模型读的是"需求要做什么"，不是"花了多少人日"。AI 让研发做得更快，但需求要动的系统、接口和页面不会因此变少。

**一把不变的尺子**

```
尺子 = 固定的模型版本 + 固定的提示词版本 + 固定的知识库快照版本
```

三者都不变时，同一份需求文档任何时候量出来都是同一个分数。

**分工原则**：大模型只负责"数数"（提取要素），算分和定档由程序按冻结的权重完成。这样结果可复算，也便于审计。

---

## 三、规模要素

| 要素 | 含义 | 示意权重 |
|---|---|---|
| 涉及系统数 | 需要改动或部署的应用个数 | ×5 |
| 接口变更数 | 新增 + 修改的接口个数 | ×2 |
| 页面 / 交互数 | 新增或改动的页面、交互个数 | ×1 |
| 外部协同方数 | 需要协同的第三方、监管、其他战场 | ×3 |
| 是否新业务 | 新产品或新渠道为"是"，存量迭代为"否" | 是 = +5 |

> 权重为示意值，实际权重由基线期数据校准得出（见第六节）。

**明确不用的数据**
- 代码行、提交数、改动文件数：AI 会放大这些数。
- 人日：会随效能提升漂移。
- "整体复杂度"这类主观判断：不让模型做，只让它数数。

---

## 四、举例

需求："信贷战场新增某渠道授信申请流程"。大模型读完需求文档，再查信贷知识库中"授信申请"对应的系统：

| 要素 | 大模型提取结果 | 权重 | 得分 |
|---|---|---|---|
| 涉及系统 | 3 个（H5 前端、授信服务、风控网关） | ×5 | 15 |
| 接口变更 | 4 个（新增 2、修改 2） | ×2 | 8 |
| 页面 / 交互 | 5 个 | ×1 | 5 |
| 外部协同方 | 1 个（渠道方） | ×3 | 3 |
| 是否新业务 | 是 | +5 | 5 |
| **要素分** | | | **36 → M 档** |

**需求当量** = 36 × k（设 k = 0.8）= **28.8 基线等价人日**，意思是"按 AI 之前的平均效率，这个需求约值 28.8 人日的活"。

团队用 AI 实际只花了 18 人日：

| 定档方式 | 结果 | 效果 |
|---|---|---|
| 按实际人日 | 18 人日 → S 档 | 提效被分档吃掉 |
| 按大模型要素 | 仍是 M 档、28.8 当量 | 节省的 10.8 人日完整体现在效率指数里 |

**示意档位切分**（实际切分点由基线期分位数确定）：XS < 10 分，S 10–24 分，M 25–49 分，L ≥ 50 分。

## 五、前提：战场产品知识库

需求文档里常常只写"新增某渠道授信流程"，不会写清楚要动哪几个系统。大模型需要知识库，才能把业务语言翻译成系统影响面。

### 5.1 最小可用知识库（每个战场一套）

| 内容 | 作用 | 冷启动来源（尽量用现有数据，不靠人从零写） |
|---|---|---|
| 应用目录 + 职责说明 | 知道有哪些系统、各管什么 | 发布系统的应用清单；职责说明由战场架构师补充 |
| 接口目录 | 识别接口变更 | 应用发布系统（应用和接口在同一个系统） |
| 业务能力 → 系统映射 | 把"授信申请"翻译成"H5 + 授信服务 + 风控网关" | 从历史上挂了 PR 的需求中自动归纳（需求 → PR → 应用），再由战场架构师确认 |
| 历史需求案例库 | 给大模型当参照 | 挂了 PR 的历史需求：需求文本 + 实际改动的应用 |

现有的 PR 挂接虽然覆盖率不高，但正好可以用来**冷启动"业务能力 → 系统映射"和案例库**，不需要全量。

### 5.2 分工

| 角色 | 职责 |
|---|---|
| 各战场架构师 | 建设和维护本战场知识库：补职责说明、确认业务能力映射、抽查偏离样本 |
| PM 团队 | 制定知识库标准、做就绪验收、按季度发布知识库快照版本 |
| 数据团队 | 拉取发布系统和 PR 数据、跑大模型定档、出核验报告 |

### 5.3 知识库不只服务于度量

AI 研发工具同样需要这套知识库：AI 写代码时要知道系统边界和接口。所以它是 **AI 转型的公共基础设施**，可以借 AI 转型的名义推动，而不是单纯为了"记账"。

### 5.4 知识库就绪标准（按战场判定）

达到以下三条，该战场才从 TL 兜底档切换到大模型档：

| 标准 | 定义 | 门槛 |
|---|---|---|
| 应用目录覆盖率 | 近 6 个月有发布记录的应用中，目录里有职责说明的比例 | ≥ 90% |
| 系统识别召回率 | 在挂了 PR 的需求样本上，实际改动的应用中被大模型识别出来的比例 | ≥ 70%（试点后校准） |
| 文档充分率 | 近 3 个月上线需求中，被大模型判为"文档充分"的比例 | ≥ 60% |

## 六、文档质量参差怎么办

iSmart 里的需求文档质量参差，有的只有标题或一两句话。

1. **先判充分度，再定档。** 大模型先判断文档信息够不够定档。不够的不硬定档，回退到 TL 档并打标记，避免"瞎猜"。
2. **知识库补位。** 描述很短的需求，大模型可以靠业务能力映射和相似历史案例推断影响面。
3. **公示文档充分率。** 按战场公示，纳入 V4。不强制，但让文档质量变得可见。
4. **防"AI 写的文档更长"导致虚高。** 只提取结构化计数，不做主观判断；每月监控要素分和文档长度的相关性，相关性明显上升就复查。

## 七、权重校准与换尺子

### 7.1 一次校准、之后冻结

1. **量基线**：用尺子 v1 量基线期（AI 推广前 6 个月）的全部历史需求文档。
2. **回归**：剔除 V1 / V3 异常的需求后，用规模要素对实际人日做回归，得出各要素权重。基线期人日虽有噪声，但样本够多时噪声相互抵消，而且只用这一次。
3. **切档**：按基线期要素分的分位数切出 XS / S / M / L，使基线期各档占比和历史人日分档大致一致，新旧口径好衔接。
4. **算 k 值**：

```
k = 基线期名册可用人日 ÷ 基线期上线需求的要素分总和
```

文档不足的基线需求，按其 TL 档所在档位的平均要素分补齐。这样基线期的效率指数正好等于 1.00。

5. **冻结**：权重、切档点、k 值定下后冻结，每年复核一次。

**算例（虚拟战场 A）**：基线期 20 人 × 21 工作日 × 6 个月 = 2,520 可用人日；基线期上线需求要素分总和 3,150；k = 2,520 ÷ 3,150 = **0.8**。验证：基线期效率指数 = 3,150 × 0.8 ÷ 2,520 = **1.00**。

### 7.2 换尺子

模型升级、提示词修改、知识库大版本更新，都算换尺子。

- **接续方法**：用新旧两把尺子同时量最近 3 个月的需求，按比例调整 k 值，使前后趋势连续：

```
k_新 = k_旧 × 旧尺子要素分总和 ÷ 新尺子要素分总和
```

- **算例**：重叠期 3 个月，旧尺子量出 1,500 分，新尺子量出 1,650 分；k_新 = 0.8 × 1,500 ÷ 1,650 ≈ **0.727**。
- **控制换尺子频率**：知识库日常小更新先累积，按季度发布一次快照版本，避免尺子天天变。

## 八、核验（不新增人工填写）

| 核验方式 | 做法 | 频率 |
|---|---|---|
| PR 样本对照 | 在挂了 PR 的需求上，对比大模型识别的系统和实际改动的应用，计算召回率和准确率 | 每季度 |
| 重复测量稳定性 | 同一批需求隔周重跑，一致率应 ≥ 95%；不一致说明提示词或参数需要收紧 | 每次换尺子 + 每季度抽查 |
| 战场级总量交叉验证 | 每个战场当月发布涉及的接口变更数（同一接口同月只计一次），与该战场需求当量的趋势对比，长期背离就复查 | 每月 |
| 依据可追溯 | 每个要素都带出处，任何人对某个需求的档位有疑问，都可以查看大模型的依据 | 随时 |

**召回率与准确率的定义**（以涉及系统为例）
- 召回率 = 实际改动且被大模型识别出的应用数 ÷ 实际改动的应用数
- 准确率 = 实际改动且被大模型识别出的应用数 ÷ 大模型识别出的应用数

**安全**：使用公司内部部署的模型；只读需求文档和知识库，不读 AI 会话原文，不涉及个人数据。

## 九、兜底：TL 评估人日档

- **适用**：知识库未就绪的战场；知识库已就绪但文档不足的需求。
- **来源**：TL 排期时已经在填的评估人日档，零新增动作。
- **已知偏差**：AI 提效后 TL 会估得越来越少，档位逐渐下漂，效率被**低估**。偏差方向已知，账是偏保守的，审计上说得过去。
- **标注**：看板上对兜底部分明确标注"偏保守"。

**对比算例（虚拟战场 A，当期滚动 3 个月）**：同一批 131 个上线需求，

| 定档方式 | 当量合计 | 名册可用人日 | 效率指数 |
|---|---|---|---|
| 大模型档 | 1,200 | 1,008 | **1.19** |
| TL 兜底档（已下漂） | 1,010 | 1,008 | **1.00**，看起来"没有提效" |

## 十、PR 挂接的定位

- **不硬推**，也不作为定档前提。
- 只作为**知识库冷启动**和**核验**的样本来源。
- P0 先按战场统计当前挂接率，判断样本够不够用；样本少到无法核验的战场（例如每季度少于 30 个），再单点推动。
- 从 PR 中只提取需求号、仓库和应用，**不提取提交人**。

## 十一、技术设计要点

### 11.1 处理流程

```
需求文档（iSmart）
   │
   ├─→ 知识库检索：应用目录片段、业务能力映射、相似历史案例（检索参数固定，属于尺子的一部分）
   │
   ▼
大模型提取（固定模型版本、固定提示词、温度 = 0）
   │  输出：文档充分度 + 各要素计数 + 依据
   ▼
程序计算：要素分 = Σ 权重 × 要素；按切档点定档；当量 = 要素分 × k
   │
   ▼
写入：需求定档结果表（带尺子版本号）
```

### 11.2 提示词骨架

```
角色：你是 {战场} 的需求规模分析员，只负责"数数"，不评价难度。
输入：
  1. 需求文档：{需求标题、描述、附件正文}
  2. 知识库检索结果：{应用目录片段}、{业务能力映射}、{相似历史案例 top-5}
规则：
  1. 先判断文档是否足以识别涉及系统；不足则输出"不足"并说明原因，不再计数。
  2. 只计文档明确提到的，或可由知识库唯一确定的项；不确定的不计，并标注。
  3. 每个计数都必须给出依据（引用文档段落或知识库条目）。
  4. 不输出整体复杂度、难度、工作量判断。
输出：严格按下方 JSON 结构。
```

### 11.3 输出结构

```json
{
  "需求ID": "REQ-12345",
  "尺子版本": { "模型": "内部模型-v3.2", "提示词": "v1.0", "知识库快照": "A-2026Q4" },
  "文档充分度": "充分",
  "不足原因": null,
  "要素": {
    "涉及系统": { "数量": 3, "清单": ["H5前端", "授信服务", "风控网关"], "依据": ["需求文档§2", "知识库:授信申请"] },
    "接口变更": { "新增": 2, "修改": 2, "依据": ["需求文档§3"] },
    "页面交互": { "数量": 5, "依据": ["需求文档§4 原型说明"] },
    "外部协同方": { "数量": 1, "清单": ["渠道方"], "依据": ["需求文档§1"] },
    "是否新业务": { "值": true, "依据": ["需求文档§1"] }
  },
  "不确定项": []
}
```

要素分、档位、当量由程序计算后另行写入，不由大模型输出。

## 十二、试点流程（以虚拟"战场 A"示范）

实际试点战场按"系统边界清楚、历史 PR 挂接较多"的标准再选。

| 周次 | 步骤 | 负责 | 产出 / 判定 |
|---|---|---|---|
| 第 1–2 周 | **数据准备**：拉取战场 A 近 12 个月（含基线期）的需求文档、发布记录、PR 挂接样本；用通用提示词抽样测文档充分率 | 数据团队 | 文档充分率底数、PR 样本量 |
| 第 3–6 周 | **知识库冷启动**：从发布系统导出应用目录和接口目录；架构师补职责说明；从 PR 样本归纳业务能力映射，架构师逐条确认；整理案例库 | 战场 A 架构师、数据团队 | 知识库 v1 |
| 第 7–8 周 | **尺子 v1 定版**：固定模型版本、提示词和知识库快照 A-v1；稳定性测试；PR 样本召回率测试 | 数据团队、PM 团队 | 重跑一致率 ≥ 95%；召回率达标或列出知识库缺口 |
| 第 9–10 周 | **基线校准**：量基线期全部需求 → 回归权重 → 切档 → 计算 k | 数据团队 | 权重表、切档点、k 值；基线期效率指数 = 1.00 |
| 第 11 周起 | **双轨运行 2–3 个月**：大模型档与 TL 档并行；输出两者的档位一致性矩阵；偏离大的样本由架构师抽查，问题回流到知识库 | 数据团队、战场 A 架构师 | 双轨报告 |
| 双轨结束 | **切换判定**：三条就绪标准全部达标，且双轨期没有系统性偏差 | PM 团队验收 | 战场 A 切换到大模型档 |

**未达标时**
- 召回率不足：先补知识库（通常是业务能力映射缺失），再测。
- 文档充分率不足：继续使用 TL 兜底档，并按战场公示文档充分率。
