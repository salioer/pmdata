# 项目交接：研发数据体系方案

> 用途：上下文压缩或开新窗口时，先读这份文档，再读 `CLAUDE.md`，就能无损接着做。
> 更新时间：2026-10-18；对应方案版本 v1.5；对应提交 `cfc93fb` 之后。

## 一、项目是什么

- **用户**：CIO 团队 PM 团队负责人（salioer）。公司在做 AI 转型，AI 研发模式正在替代部分数马人力。
- **要做的两件事**：① 建一本可审计的账，度量研发效能、人效、AI 效能；② 治理已经腐化的存量数据体系。
- **原始输入**：`init_prompt.md`（角色、五个问题、坐标系、工时守恒原理、四类数据资产、7 项产出要求）。
- **产出**：一份方案文档 + 一个可视化 HTML + 一份指标字典 CSV，全部在仓库 `salioer/pmdata` 的 `main` 分支。

## 二、文件与协作方式

| 文件 | 说明 |
|---|---|
| `docs/研发数据体系方案.md` | **唯一内容来源**。结构为"总述 → 第一至第九部分 → 总结 → 附录"（总分总） |
| `docs/研发数据体系方案.html` | 由 md 生成的可视化阅读版，Artifact 片段格式（不含 doctype / html / head / body） |
| `metrics/指标字典.csv` | 29 个指标，UTF-8 带 BOM，由 `tools/gen_indicator_csv.py` 生成 |
| `tools/gen_indicator_csv.py` | 指标字典生成脚本：改指标就改这里的 ROWS，再重新生成 |
| `tools/check_consistency.py` | 核对 CSV 与文档"指标总表""指标 × 校验对照"是否一致 |
| `CLAUDE.md` | 协作约定（会被自动加载） |
| `README.md` | 仓库目录入口 |

**Artifact 链接**：https://claude.ai/artifact/TxtjY2MWvLj3t4SnRDAPg7 （私有，当前为第 5 版）。新会话更新时，发布要传入这个 `url`，否则会生成新链接。

**和用户的交互方式（重要）**

1. **方案从文档来，展示用 HTML**：先改 md，再同步 HTML，再重新发布到同一个链接，最后提交推送到 `main`。
2. **先讨论、后改文件**：用户提出新问题或新想法时，先在聊天里给设计（可以用表格、算例），**用户明确确认后才更新文件**。用户说"先不用更新文件""我确认后再更新"时，严格遵守。
3. **语言**：中文、平实，术语首次出现要解释；用户常追问"这是什么意思"，回答要配具体例子。
4. **算例**：统一用虚拟"战场 A"。改动数字后要验算：基线期效率指数 = 1.00，桥接表每月平衡，三个月上线合计 131。

**每次更新的标准流程**

1. 改 `docs/研发数据体系方案.md`，版本号 +0.1，版本行写明本次改动。
2. 指标有变化时：改 `tools/gen_indicator_csv.py` → 重新生成 CSV（`{ printf '\xef\xbb\xbf'; python3 tools/gen_indicator_csv.py; } > metrics/指标字典.csv`）→ 跑 `python3 tools/check_consistency.py`。
3. 同步改 HTML（版本号在三处：侧栏 brand、封面 meta、页脚）。改完检查标签配平和脚本语法；改了图表或布局时，用 Playwright 截一次图（`reducedMotion: 'reduce'`，否则平滑滚动会导致截图错位；Chromium 在 `/opt/pw-browsers`，playwright 在 `/opt/node22/lib/node_modules/playwright`）。
4. 发布 Artifact（同一文件路径或传 `url`），提交并推送 `main`。

## 三、已确认的决策（按主题）

**组织与范围**
- 四个战场：消金、信贷、支付、保险。antom 是其中一个战场，有自有项目管理系统，接口同步到 iSmart。
- 研发力量：正式 + 数马；外包已裁撤，只在基线期作为历史类别。
- 读者是所有人；但看板分内外：研发内部 L1–L3，业务团队只看"业务版"。

**北极星与当量**
- 效率指数 = Σ 上线需求当量 ÷ Σ 名册可用人日；按战场、滚动 3 个月；基线期（AI 推广前连续 6 个月）= 1.00。
- 分母用名册（在册人数 × 工作日），不用工时明细——依据工时守恒：总量可信，分配不可信。
- 需求当量 = 档位权重 × k；档位权重 = 基线期该档实际人日中位数（示意 XS 2、S 6、M 18、L 45）；k 使基线期效率指数 = 1.00（算例 k = 1.2）。
- 用户曾质疑"当量和需求数 / 实际人日有什么区别"，文档 3.3 已用两个反例和"期初规模"三问题解释清楚。

**规模定档**
- 用 TL 排期时的评估人日定档，随排期快照冻结（示意阈值 XS ≤ 3、S 4–10、M 11–30、L > 30）。
- 每月纠偏：**只按实际上调，不按实际下调**；差一档不改；跨两档以上实际更高则自动上调（工时归属校验红灯时转 TL 确认）；实际更低默认保持，TL 确认范围缩减 / 拆单才下调。
- 被否决的方案：修改点定档（放入第九部分作为远期方向）、TL 填修改点（推行不了）、PR 自动关联（推了 4 个月仍难强制）、PM 填修改点（PM 缺少复杂度判断能力）、大模型 + 知识库（可行但前提重）。
- 免排期范式化需求：按**范式档位表**定档，由**战场架构师维护**，季度复核；匹配不到默认 XS。
- 配置类需求：不定档、不进效能统计、只计吞吐量（AI 推广前后一致）。

**排期与时间**
- 三种排期：传统排期（每月；含上月延续 + 本月新进）、快速排期（每 2 周一个窗口）、免排期（AI 后新增；分配置类和范式化研发需求）。
- 跨月需求约 30%，研发周期 P85 约 30 天 → 3 个月滚动窗口足够；窗口规则：不短于 P85，P85 超过 60 天改 6 个月。
- 北极星只用产出口径（上线月）；承诺口径只看兑现率。在制调整版效率为备选，等状态数据校验转绿再启用。
- 桥接表按排期类型拆成 ①本月新进 ②往期延续 ③快速排期 ④免排期 ⑤计划外插入，另列在制变化和配置类吞吐量。

**业务体感（v1.5 新增）**
- IN = 进入排期快照的需求（含上月延续，带"已排期第几个月"属性）；OUT = 研发带宽不够顺延到下月，每月都计入分母，OUT 后可能被业务取消。
- 需求吞吐率 F01 = IN ÷ (IN + OUT)，**只算传统排期**（快速排期没有 OUT）。
- 业务版指标：F01 需求吞吐率、F02 需求积压、F03 端到端交付周期（自然日，分等排期 / 研发两段）、F04 小需求响应时长；共用 E03 月交付需求数、E05 承诺兑现率、E06 排期移出率。
- 业务版**不出现当量、规模档、人日、人效、AI 成本、故障指标**；只放结论级指标；不用红黄绿，只看相对 AI 推广前的变化方向。
- E06 定为"排期移出率"（本月移出数 ÷ 本月排期数），**不再计算计划膨胀率**。

**数据保障**
- 原 V1–V8 收拢为五个域、15 项校验：① 人力与工时 1.1–1.4、② 需求 2.1–2.4、③ 规模档 3.1–3.3、④ 时间与排期 4.1–4.2、⑤ AI 与成本 5.1–5.2；每项写明保障哪些指标；附录 C 有原编号对照。V1–V7 与用户内部定义一致。
- 数据门禁：结论级 / 底数级 / 不出；依赖校验任一为红则降为底数级。
- 字段级权威源、antom 状态映射与冲突裁决见 6.4。
- 红线：最小必要、匿名聚合（最细到战场 × 团队 × 周）、不进 KPI、不读会话原文、访问留痕。
